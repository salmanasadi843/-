# قرارداد اولیه Backend API درس‌یار — نسخه 1

وضعیت: قرارداد هدف نسخه 1 برای staging. بخشی از endpointهای دامنه‌ای در Backend آزمایشی پیاده‌سازی و با PostgreSQL موقت آزموده شده‌اند. Android اکنون یک صفحه مرور سلسله‌مراتبی staging دارد که علاوه بر خواندن، ویرایش/حذف نرم/بازیابی کلاس و جلسه، جابه‌جایی و مرتب‌سازی جلسه و عملیات یادداشت/وضعیت شخصی را از API انجام می‌دهد؛ این صفحه هنوز جریان اصلی Room/Firestore را جایگزین نکرده و همگام‌سازی Room ندارد. API در محیط عملیاتی مستقر نشده است.

## وضعیت پیاده‌سازی فعلی (بازبینی کد در 2026-11-05)

مسیرهای زیر در `backend/src/main/kotlin/ir/darsyar/backend/Application.kt` ثبت شده‌اند و پشت احراز هویت Firebase قرار دارند، مگر health/readiness و معرفی API:

- `GET /health/live`, `GET /health/ready`, `GET /api/v1`, `GET /api/v1/me`, `GET /api/v1/teachers` (فقط استادانی که حداقل یک کلاس قابل مشاهده دارند؛ بدون افشای ایمیل).
- درخواست استادی: `POST /api/v1/teacher-applications`; مدیریت مدیر: `GET /api/v1/admin/teacher-applications` و `PATCH /api/v1/admin/teacher-applications/{userId}`.
- پوشه استاد: `GET/POST /api/v1/teacher-folders`, `PATCH/DELETE /api/v1/teacher-folders/{folderId}`.
- کلاس‌ها: `GET/POST /api/v1/classes`, `GET /api/v1/classes/deleted`, `PATCH/DELETE /api/v1/classes/{classId}`, `POST /api/v1/classes/{classId}/restore`.
- دوره‌ها: `GET/POST /api/v1/classes/{classId}/courses`, `PATCH/DELETE /api/v1/courses/{courseId}`.
- جلسات: `GET/POST /api/v1/classes/{classId}/sessions`, `GET /api/v1/classes/{classId}/sessions/{sessionId}`, `PATCH/DELETE /api/v1/sessions/{sessionId}`, `POST /api/v1/sessions/{sessionId}/restore`.
- فهرست جلسه‌ها فقط metadata خلاصه را برمی‌گرداند؛ transcript، متن اصلی، خلاصه هوشمند و نکات کلیدی فقط از endpoint جزئیات همان جلسه انتخاب‌شده دریافت می‌شود. جزئیات با همان قواعد visibility سمت سرور و query محدود به classId و sessionId کنترل می‌شود.
- منابع صوتی: `GET/POST /api/v1/sessions/{sessionId}/audio-sources`, `PATCH/DELETE /api/v1/sessions/{sessionId}/audio-sources/{sourceId}`.
- کد ورود: `GET/POST /api/v1/classes/{classId}/access-codes`, `DELETE /api/v1/access-codes/{codeId}`, `POST /api/v1/class-memberships/redeem`.
- عضویت: `GET /api/v1/classes/{classId}/memberships`, `DELETE /api/v1/classes/{classId}/memberships/{studentUserId}`.
- اعلان‌های رسمی کلاس: `GET/POST /api/v1/classes/{classId}/announcements` و `DELETE /api/v1/classes/{classId}/announcements/{announcementId}`؛ فقط مالک کلاس یا مدیر اعلان منتشر/حذف می‌کند. اعضای فعال کلاس اعلان درون‌برنامه‌ای می‌گیرند و نویسنده اعلان به خودش اعلان نمی‌گیرد. مشاهده اعلان‌های کلاس عمومی برای کاربران احراز هویت‌شده مجاز است؛ کلاس خصوصی فقط برای مالک، مدیر و عضو فعال قابل مشاهده است.
- تالار گفتگو: `GET/POST /api/v1/classes/{classId}/forum/topics`, `GET/POST /api/v1/forum/topics/{topicId}/posts`, `PATCH /api/v1/forum/topics/{topicId}/moderation` برای سنجاق/قفل؛ بحث می‌تواند به یک جلسه همان کلاس متصل باشد.
- ویرایش بحث: `PATCH /api/v1/forum/topics/{topicId}` و حذف نرم بحث: `DELETE /api/v1/forum/topics/{topicId}`؛ نویسنده، مالک کلاس و مدیر اصلی مجازند.
- ویرایش پاسخ: `PATCH /api/v1/forum/posts/{postId}` و حذف نرم پاسخ: `DELETE /api/v1/forum/posts/{postId}`؛ نویسنده پاسخ، مالک کلاس و مدیر اصلی مجازند. حذف، رکورد را از نمایش عادی خارج می‌کند و داده خام را فوراً پاک نمی‌کند.
- اعلان‌ها: `GET /api/v1/notifications?unreadOnly=true|false`, `POST /api/v1/notifications/{notificationId}/read`. هر دو مسیر فقط inbox کاربر احراز هویت‌شده را هدف می‌گیرند؛ فهرست با `recipient_user_id` محدود است و علامت‌گذاری خوانده‌شدن نیز فقط برای همان گیرنده انجام می‌شود. اعلان بحث تازه/پاسخ به مالک کلاس و اعضای فعال یا مشارکت‌کنندگان مرتبط می‌رسد؛ mention فقط به مالک یا عضو فعال می‌رسد و با اعلان همان رویداد تکرار نمی‌شود. در کلاس عمومی، کاربر غیرعضو می‌تواند بحث عمومی ثبت کند، اما اعلان‌های کلاسی برای او یا سایر غیرعضوها صادر نمی‌شود. نویسنده برای رویداد خودش اعلان نمی‌گیرد. ارسال push notification هنوز پیاده نشده است.
- Migration `V4__class_forums_and_notifications.sql` جداول موضوع‌ها، پاسخ‌های چندسطحی و inbox اعلان را اضافه می‌کند؛ `V5__class_announcements.sql` تابلوی اعلان رسمی کلاس و نوع اعلان مربوط را اضافه می‌کند.

دسترسی عمومی بدون ورود اکنون به‌صورت محدود پیاده‌سازی شده است: `GET /api/v1/public/classes` فهرست کلاس‌های عمومی، منتشرشده و غیرمخفی را بدون Firebase token برمی‌گرداند؛ `GET /api/v1/public/classes/{classId}/sessions` فقط جلسه‌های منتشرشده همان کلاس را برمی‌گرداند؛ و `GET /api/v1/public/classes/{classId}/sessions/{sessionId}` جزئیات متن جلسه را فقط در صورت عمومی و منتشرشده بودن کلاس و جلسه ارائه می‌کند. این سه مسیر خارج از `authenticate("firebase")` هستند و فیلترهای کلاس/جلسه در SQL اعمال می‌شوند. سایت وب نیز در صفحه ورود، کاتالوگ عمومی و متن جلسه را نمایش می‌دهد. دسترسی ناشناس به کلاس خصوصی، جلسه منتشرنشده، کلاس مخفی یا محتوای حذف‌شده مجاز نیست. آزمون PostgreSQL برای جداسازی جلسه عمومی از خصوصی/منتشرنشده افزوده شده؛ پذیرش نهایی منوط به سبزشدن CI است. مسیر مستقل جزئیات کلاس و صفحه‌بندی فهرست هنوز پیاده نشده‌اند.

صفحه `BackendBrowseScreen` در Android مرور سلسله‌مراتبی استاد ← کلاس ← جلسه را انجام می‌دهد و عملیات مجاز ویرایش کلاس/جلسه، حذف نرم و بازیابی، جابه‌جایی جلسه بین کلاس‌ها، تغییر ترتیب جلسه، یادداشت شخصی و وضعیت پخش را از API staging فراخوانی می‌کند. این صفحه در عین حال صفحه ایجاد کلاس/جلسه و جایگزین کامل جریان اصلی اپ نیست؛ اتصال نوشتن/همگام‌سازی با Room و صف آفلاین هنوز فعال نشده است. نام تاریخی `DarsyarReadOnlyApi` دیگر توصیف کاملی از متدهای آن نیست و شامل عملیات mutation نیز هست. این فهرست، مسیرهای ثبت‌شده در کد است و به‌معنی تکمیل همه نیازهای محصول یا اتصال عملیاتی کلاینت نیست. مواردی مانند `POST /api/v1/auth/exchange`، فهرست ثبت‌نام‌های کاربر، endpointهای sync، صفحه‌بندی cursor-based، وضعیت شخصی جلسه و OpenAPI کامل هنوز در این فاز به‌عنوان قرارداد هدف/کار باقیمانده‌اند. نام‌های قرارداد اولیه مانند `teacher-requests` و `classes/{classId}/join` با مسیر واقعی فعلی یکسان نیستند؛ مسیرهای بالا مرجع پیاده‌سازی فعلی‌اند.

آزمون‌های CI با PostgreSQL موقت، مجوزهای مسیرهای کلاس، پوشه، دوره، جلسه، صوت، کد ورود و عضویت را بررسی می‌کنند. موفقیت CI staging به‌تنهایی پذیرش امنیتی یا مجوز استقرار عملیاتی نیست.

## 1. اصول قرارداد

- Android و Web فقط از HTTPS API استفاده می‌کنند؛ دسترسی مستقیم کلاینت به PostgreSQL ممنوع است.
- مسیرها با `/api/v1` نسخه‌بندی می‌شوند.
- شناسه‌های مقصد UUID هستند. شناسه‌های عددی Room فقط در `legacy_id_map` باقی می‌مانند.
- همه زمان‌ها در API به ISO-8601 UTC ارسال می‌شوند. تبدیل به تاریخ شمسی فقط در UI انجام می‌شود؛ مقدار epoch قدیمی در import حفظ و قابل تطبیق می‌ماند.
- صفحه‌بندی فهرست‌ها cursor-based است؛ endpoint نباید همه کلاس‌ها/جلسات را یکجا برگرداند.
- عملیات نوشتن باید idempotency و کنترل نسخه داشته باشند.
- حذف منطقی (tombstone) تا پایان پنجره همگام‌سازی نگهداری می‌شود؛ پاک‌سازی فیزیکی فقط با سیاست نگهداری و backup.

## 2. احراز هویت در دوره گذار

1. Android/Web در مرحله اول Firebase Auth فعلی را حفظ می‌کنند.
2. کلاینت Firebase ID Token را در `Authorization: Bearer <token>` می‌فرستد.
3. آداپتور احراز هویت Backend توکن را با Firebase Admin SDK و پروژه مورد انتظار اعتبارسنجی می‌کند.
4. Backend از `auth_identities(provider='firebase', provider_subject=uid)` کاربر داخلی را پیدا می‌کند؛ در صورت نبود نگاشت، فقط مسیر onboarding مجاز می‌تواند آن را ایجاد کند.
5. نقش‌ها و تأیید استاد از جداول Backend خوانده می‌شوند، نه از body درخواست، SharedPreferences یا ادعای کلاینت.
6. مدیر اصلی فقط از فرایند bootstrap امن و ثبت‌شده در محیط سرور تعیین می‌شود؛ ایمیل یا UID ارسالی کاربر، مجوز مدیر ایجاد نمی‌کند.
7. در آینده می‌توان آداپتور Firebase را با ارائه‌دهنده هویت دیگری جایگزین کرد، بدون تغییر شناسه داخلی کاربر و داده‌های آموزشی.

کلید service account فقط در secrets سرور است؛ هرگز در APK، وب‌سایت عمومی، Git یا Docker image قرار نمی‌گیرد.

## 3. قرارداد پاسخ و خطا

موفقیت، JSON با ساختار endpoint-specific برمی‌گرداند. خطاها از ساختار ثابت زیر استفاده می‌کنند:

```json
{
  "error": {
    "code": "FORBIDDEN",
    "message": "You do not have permission to perform this action.",
    "requestId": "server-generated-id",
    "details": {}
  }
}
```

کدهای مهم:
- `400 VALIDATION_ERROR`
- `401 UNAUTHENTICATED`
- `403 FORBIDDEN`
- `404 NOT_FOUND` (بدون افشای وجود محتوای خصوصی)
- `409 VERSION_CONFLICT`
- `409 IDEMPOTENCY_KEY_REUSED`
- `429 RATE_LIMITED`
- `500 INTERNAL_ERROR`

پیام قابل نمایش فارسی در کلاینت نگاشت می‌شود؛ جزئیات داخلی، SQL، token و stack trace به کاربر برگردانده نمی‌شود.

## 4. Endpointهای اولیه

### هویت و پروفایل

- `POST /api/v1/auth/exchange` — اعتبارسنجی توکن گذار و دریافت شناسه داخلی/پروفایل.
- `GET /api/v1/me` — کاربر، نقش‌ها، وضعیت و مجوزهای خلاصه.
- `GET /api/v1/me/enrollments` — کلاس‌های خصوصی/عمومی مجاز کاربر.
- `POST /api/v1/teacher-requests` — درخواست تأیید استادی.
- `GET /api/v1/admin/teacher-requests` — فهرست درخواست‌ها، فقط مدیر.
- `POST /api/v1/admin/teacher-requests/{requestId}/approve`
- `POST /api/v1/admin/teacher-requests/{requestId}/reject`

### پوشه، کلاس، درس و جلسه

- `GET /api/v1/teachers/{teacherId}/folders`
- `POST /api/v1/teacher-folders`
- `PATCH /api/v1/teacher-folders/{folderId}`
- `DELETE /api/v1/teacher-folders/{folderId}`
- `GET /api/v1/classes` (فهرست قابل‌مشاهده برای حساب احراز هویت‌شده؛ cursor/limit در نسخه فعلی پیاده نشده است)
- `POST /api/v1/classes`
- `PATCH /api/v1/classes/{classId}`
- `DELETE /api/v1/classes/{classId}`
- `GET /api/v1/classes/{classId}/courses`
- `POST /api/v1/classes/{classId}/courses`
- `PATCH /api/v1/courses/{courseId}`
- `DELETE /api/v1/courses/{courseId}`
- `GET /api/v1/classes/{classId}/sessions` — فهرست خلاصه بدون متن جلسه.
- `POST /api/v1/classes/{classId}/sessions`
- `GET /api/v1/classes/{classId}/sessions/{sessionId}` — جزئیات کامل فقط برای جلسه انتخاب‌شده و پس از کنترل مجوز.
- `PATCH /api/v1/sessions/{sessionId}`
- `DELETE /api/v1/sessions/{sessionId}`

### انتشار و کلاس خصوصی

- `POST /api/v1/classes/{classId}/publish`
- `POST /api/v1/classes/{classId}/unpublish`
- `POST /api/v1/classes/{classId}/access-codes`
- `POST /api/v1/classes/{classId}/join` — کد ورود یا دعوت؛ کد خام در URL یا log ثبت نمی‌شود.
- `DELETE /api/v1/classes/{classId}/members/{userId}`

### صوت و وضعیت شخصی

- `GET/POST /api/v1/sessions/{sessionId}/audio-sources`
- `PATCH/DELETE /api/v1/audio-sources/{sourceId}`
- `GET /api/v1/classes/{classId}/sessions/{sessionId}/state` — دریافت علاقه‌مندی و موقعیت پخش شخصی کاربر؛ فقط برای جلسه‌ای که کاربر مجاز به مشاهده آن است.
- `PUT /api/v1/classes/{classId}/sessions/{sessionId}/state` — ذخیره هم‌زمان علاقه‌مندی و موقعیت پخش شخصی؛ داده برای هر کاربر جداست و موقعیت باید بین صفر تا هفت روز باشد.
- یادداشت‌های شخصی جلسه: `GET/POST /api/v1/classes/{classId}/sessions/{sessionId}/notes` و `PATCH/DELETE /api/v1/session-notes/{noteId}`؛ هر یادداشت به حساب نویسنده محدود است و می‌تواند متن نقل‌شده و بازه انتخاب در transcript را نگه دارد. حذف نرم انجام می‌شود.
- Migration `V6__personal_session_notes.sql` جدول یادداشت‌های خصوصی هر کاربر را با کلید خارجی جلسه و ایندکس فهرست فعال اضافه می‌کند.

### مدیر اصلی

- `GET /api/v1/admin/teachers`
- `GET /api/v1/admin/teachers/{teacherId}/content`
- عملیات مدیریت محتوا از endpointهای عمومی با مجوز super_admin یا مسیرهای اختصاصی admin؛ انتخاب نهایی باید در OpenAPI مشخص شود.
- همه عملیات cross-owner در audit log ثبت می‌شوند.

### قرارداد پیشنهادی پرسش از هوش مصنوعی (هنوز پیاده‌سازی نشده)

مسیر پیشنهادی برای نسخه اول:

`POST /api/v1/classes/{classId}/sessions/{sessionId}/ai/answer`

درخواست فقط شامل سؤال کاربر و در صورت نیاز متن انتخاب‌شده از همان جلسه است؛ کل transcript نباید از کلاینت دوباره ارسال شود، چون سرور نسخه معتبر آن را در اختیار دارد.

```json
{
  "question": "استاد در این بخش چه دلیلی برای ... مطرح می‌کند؟",
  "selectedText": "بخش انتخاب‌شده اختیاری"
}
```

پاسخ پیشنهادی شامل `answer` و ارجاع‌های محدود به متن جلسه (شناسه جلسه و بازه/قطعه متن، در صورت پشتیبانی بازیابی) است. پاسخ هوش مصنوعی نباید به‌عنوان متن قطعی استاد یا محتوای ذخیره‌شده جلسه معرفی شود.

الزامات امنیتی و اجرایی پیش از فعال‌سازی:
- مسیر فقط زیر احراز هویت Firebase و پس از نگاشت UID به حساب فعال برنامه اجرا شود؛ مهمان پاسخ 401 می‌گیرد.
- Backend با `sessionRepository.findVisible(userId, roles, classId, sessionId)` یا معادل هم‌ارز، مجوز مشاهده همان جلسه را پیش از هر فراخوانی مدل کنترل می‌کند. برای کلاس خصوصی، عضویت فعال لازم است؛ مدیر و مالک طبق سیاست دسترسی مجازند.
- شناسه کلاس و جلسه باید با هم تطبیق داشته باشند؛ جلسه ناموجود یا غیرقابل‌دسترسی با پاسخ 404 یکسان برگردد تا وجود محتوای خصوصی افشا نشود.
- سؤال و متن انتخابی اعتبارسنجی و محدود به طول مشخص شوند؛ محدودیت درخواست بر اساس کاربر و IP، سقف هزینه/توکن، timeout و لغو درخواست اعمال شود.
- کلید ارائه‌دهنده فقط در secretهای محیط سرور نگهداری شود؛ هرگز در APK، وب، Git، پاسخ API یا log قرار نگیرد.
- انتخاب ارائه‌دهنده/مدل از طریق آداپتور سمت سرور و تنظیمات محیطی انجام شود. هنوز ارائه‌دهنده نهایی انتخاب نشده و نباید از کلیدهای محلی Gemini/Groq اندروید استفاده شود.
- transcript، سؤال، متن خصوصی و پاسخ خام در log ثبت نشوند؛ فقط شناسه درخواست، زمان، وضعیت، مصرف تقریبی و خطای پاک‌سازی‌شده برای پایش عملیاتی ثبت شود.
- پاسخ مدل قبل از ارسال، از نظر اندازه و قالب محدود شود؛ خطاهای provider به پیام عمومی امن تبدیل شوند و retry فقط برای خطاهای گذرا و با سقف مشخص انجام شود.
- تا زمان پیاده‌سازی و آزمون این کنترل‌ها، قابلیت پرسش هوش مصنوعی در وب/Backend مشترک غیرفعال می‌ماند. این قرارداد به‌تنهایی endpoint یا قابلیت آماده ایجاد نمی‌کند.

### سیاست تجربه مهمان و امکانات تعاملی

- مهمان فقط فهرست کلاس‌های عمومی منتشرشده، جلسه‌های منتشرشده همان کلاس و جزئیات متن عمومی را از endpointهای `public` می‌خواند.
- مهمان می‌تواند متن عمومی را انتخاب و کپی کند و از جست‌وجوی محلی/معمولی یا هایلایت موقتِ محدود به همان نشست استفاده کند؛ این موارد نباید داده‌ای در حساب یا سرور ذخیره کنند.
- ذخیره و بازیابی هایلایت، یادداشت، نشانک، موقعیت مطالعه و پیشرفت مطالعه نیازمند ورود است. اگر کاربر مهمان اقدام به ذخیره کند، کلاینت باید پیام روشن ورود/ثبت‌نام نشان دهد و پس از ورود او را به همان محتوا بازگرداند.
- پرسیدن سؤال از هوش مصنوعی، جست‌وجوی معناییِ حساب‌محور و هر قابلیت هوش مصنوعی که از زمینه اختصاصی کاربر/کلاس خصوصی استفاده می‌کند نیازمند ورود و کنترل مجوز محتوا در سرور است. در حال حاضر endpoint عمومی پرسش هوش مصنوعی در قرارداد وجود ندارد؛ نباید برای مهمان ساخته یا از کلید API داخل کلاینت فراخوانی شود.
- تالار گفتگو، ثبت پاسخ، اعلان‌های شخصی، عضویت و دسترسی به کلاس خصوصی همگی نیازمند ورود هستند. کلاس خصوصی علاوه بر ورود، عضویت معتبر یا کد ورود طبق سیاست کلاس می‌خواهد.
- محدودیت مهمان باید در API نیز اعمال شود؛ نمایش/پنهان‌کردن کنترل در وب یا اندروید به‌تنهایی مرز امنیتی نیست.
- هنگام درخواست یک قابلیت محدودشده، پیام پیشنهادی: «برای استفاده از این امکان، ابتدا وارد حساب کاربری خود شوید.»؛ پس از ورود، مقصد قبلی حفظ شود تا کاربر از ادامه کار بازنماند.

## 6. کنترل نسخه و تکرارپذیری

- هر منبع قابل ویرایش دارای `version` افزایشی است.
- کلاینت در PATCH مقدار نسخه مورد انتظار را می‌فرستد؛ اگر نسخه سرور تغییر کرده باشد، پاسخ `409 VERSION_CONFLICT` است.
- هر عملیات نوشتن/تکرارشونده `Idempotency-Key` یکتا دارد.
- درخواست تکراری با همان کلید و همان body پاسخ قبلی را می‌گیرد؛ همان کلید با body متفاوت رد می‌شود.
- حذف به‌صورت tombstone و با نسخه جدید ثبت می‌شود تا دستگاه آفلاین رکورد حذف‌شده را دوباره زنده نکند.

## 7. همگام‌سازی Android و Room

فاز اتصال Android باید Room را cache محلی حفظ کند:

- `GET /api/v1/sync/changes?cursor=...` برای دریافت تغییرات از آخرین cursor.
- `POST /api/v1/sync/commands` برای ارسال فرمان‌های محلی صف‌شده، هر فرمان با شناسه یکتا، نوع عملیات، شناسه مقصد، نسخه پایه و payload.
- سرور نتیجه هر فرمان را مستقل برمی‌گرداند: پذیرفته، تعارض، ممنوع یا نیازمند حل مالکیت.
- صف محلی فقط پس از تأیید سرور علامت‌گذاری می‌شود.
- تعارض متن اصلی و متن ویرایش‌شده نباید با last-write-wins بی‌قید حل شود؛ نسخه‌ها نگهداری و برای تصمیم کاربر/سیاست مشخص عرضه می‌شوند.
- در فاز اول می‌توان نوشتن آنلاین را فعال و صف آفلاین را محدود نگه داشت؛ اما حذف cache آفلاین از دامنه طراحی نیست.

## 8. جست‌وجو و حریم خصوصی

- جست‌وجوی عمومی فقط کلاس/جلسه عمومی منتشرشده را برمی‌گرداند.
- جست‌وجوی داخل حساب فقط رکوردهایی را برمی‌گرداند که کاربر مجاز به دیدن آن‌هاست.
- transcript، originalTranscript، یادداشت‌ها و متن‌های خصوصی در index عمومی قرار نمی‌گیرند.
- pagination و rate limit برای endpointهای جست‌وجو الزامی است.

## 9. خارج از دامنه نسخه اول

- پرداخت و اشتراک
- میزبانی/پراکسی فایل صوتی
- انتقال خودکار فایل‌های محلی دستگاه
- dual-write هم‌زمان Firebase و PostgreSQL
- مهاجرت رمز عبور Firebase به‌صورت فرضی یا استخراج رمز خام
- انتشار عمومی محتوایی که مالکیت یا مجوز آن unresolved است

## 10. گام بعد از تأیید طراحی

1. تکمیل inventory داده Firestore و تعیین تکلیف unresolved ownership.
2. ساخت پروژه Ktor مستقل با health/readiness، OpenAPI و Docker.
3. افزودن Flyway و اجرای schema فقط روی PostgreSQL staging خالی.
4. پیاده‌سازی auth adapter گذار و تست نقش‌ها.
5. ساخت import/export آزمایشی idempotent با گزارش شمارش و checksum.
6. اجرای restore روی میزبان دوم/محیط جداگانه و آزمون قطع میزبان اصلی.
7. پس از موفقیت، نمونه وب و اتصال آزمایشی Android.

هیچ مرحله‌ای از این فهرست مجوز تغییر تولیدی یا انتقال واقعی داده نیست.

### تنظیمات AI و کلید API شخصی (تصمیم معماری، هنوز پیاده‌سازی نشده)

حالت پیش‌فرض:
- درخواست AI از سرویس مرکزی درس‌یار استفاده می‌کند؛ سهمیه، مدل‌های مجاز و سقف مصرف را Backend کنترل می‌کند.
- کاربر در تنظیمات می‌تواند به‌صورت اختیاری حالت «API شخصی» را فعال کند.

مسیرهای پیشنهادی حساب کاربر:
- GET /api/v1/me/ai-settings — نمایش حالت فعال، provider/model انتخاب‌شده، وضعیت کلید و اطلاعات ماسک‌شده؛ هرگز مقدار کلید را برنمی‌گرداند.
- PUT /api/v1/me/ai-settings — انتخاب central یا personal و تنظیم provider/model مجاز.
- PUT /api/v1/me/ai-credentials/{provider} — ثبت یا تعویض کلید شخصی؛ ورودی فقط از HTTPS و با احراز هویت.
- POST /api/v1/me/ai-credentials/{provider}/test — آزمون اتصال بدون افشای کلید یا متن جلسه.
- DELETE /api/v1/me/ai-credentials/{provider} — حذف کلید ذخیره‌شده.

الزامات:
- این مسیرها فقط طرح قراردادند و تا پیاده‌سازی کامل نباید در UI به‌عنوان قابلیت فعال نمایش داده شوند.
- کلید باید با envelope encryption رمز شود؛ کلید رمزگشایی در secret manager یا محیط امن جدا از DB نگهداری شود. هیچ endpointی کلید کامل ذخیره‌شده را بازنمی‌گرداند.
- کلیدها، سؤال‌ها، transcript و پاسخ‌ها در log ثبت نشوند؛ پیام خطا باید پاک‌سازی شود.
- انتخاب personal بدون credential معتبر برای provider انتخاب‌شده مجاز نیست. تغییر به central باید کلید شخصی را خودکار حذف نکند؛ حذف کلید عملیات جداگانه و صریح است.
- API key شخصی صرفاً اعتبارنامه پرداخت/مصرف نزد provider است و هرگز جایگزین احراز هویت درس‌یار، عضویت کلاس یا مجوز مشاهده جلسه نمی‌شود.
- کلید مرکزی و کلید شخصی هر دو فقط در Backend استفاده می‌شوند؛ کلاینت نباید provider را مستقیم فراخوانی کند.
- اگر کلید شخصی نامعتبر، منقضی یا quota آن تمام شد، خطای قابل فهم به همان کاربر نمایش داده می‌شود؛ fallback به سهمیه مرکزی فقط با انتخاب صریح کاربر و سیاست سهمیه فعال مجاز است.
- provider/model از allowlist سمت سرور انتخاب می‌شود؛ URL دلخواه endpoint از طرف کاربر پذیرفته نمی‌شود تا SSRF و ارسال کلید به مقصد ناخواسته رخ ندهد.
- نرخ درخواست، timeout، محدودیت ورودی/خروجی، اعتبارسنجی citation و بررسی مجوز جلسه برای هر دو حالت یکسان است.

## انتقال و مرتب‌سازی جلسه‌ها — تکمیل قرارداد مسیرهای پیاده‌سازی‌شده

در Backend آزمایشی، دو عملیات زیر در مسیر احرازشده ثبت شده‌اند:

- `POST /api/v1/sessions/{sessionId}/move` با بدنه `{"targetClassId":"<uuid>"}` برای درخواست انتقال جلسه به کلاس مقصد.
- `POST /api/v1/sessions/{sessionId}/reorder` با بدنه `{"direction":"up"}` یا `{"direction":"down"}` برای تغییر ترتیب جلسه.

نکات کلاینت:
- شناسه جلسه و کلاس مقصد باید از پاسخ API دریافت شوند؛ کلاینت نباید شناسه محلی Room را به‌جای UUID ارسال کند.
- پس از انتقال موفق، فهرست جلسه‌های کلاس مبدأ و مقصد باید دوباره دریافت شود؛ جلسه باید فقط در کلاس مقصد نمایش داده شود.
- خطای 403 به معنی نداشتن مجوز انتقال و خطای 400 به معنی نامعتبر بودن درخواست یا مقصد است. کلاینت نباید در این حالت جلسه را از cache حذف کند.
- انتقال، با حذف و ایجاد مجدد جلسه در کلاینت شبیه‌سازی نشود؛ از endpoint اختصاصی استفاده شود تا شناسه و پیوندهای محتوایی در اختیار Backend باقی بماند.
- این ثبت قرارداد به معنی فعال‌بودن انتقال در رابط Android/Web نیست. اتصال UI، آزمون سناریوهای مالکیت و بررسی حفظ تمام وابستگی‌ها باید پیش از اعلام تکمیل انجام شود.
