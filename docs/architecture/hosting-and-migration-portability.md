# راهبرد استقلال زیرساخت و قابلیت انتقال سرور درس‌یار

وضعیت: الزام معماری برای تمام پیاده‌سازی‌های آینده؛ هیچ سرور یا سرویس جدیدی در این مرحله خریداری یا مستقر نمی‌شود.

## 1. هدف و اصل بنیادین

درس‌یار باید بتواند بدون بازنویسی منطق کسب‌وکار و بدون از دست‌رفتن داده‌ها، از یک میزبان به میزبان دیگر منتقل شود؛ از جمله انتقال از Firebase فعلی به Backend مستقل، جابه‌جایی Backend میان ارائه‌دهندگان سرور، و در صورت نیاز انتقال سرور ایران به کشور یا ارائه‌دهنده دیگر.

**قابلیت انتقال به معنی آن نیست که همه سرویس‌ها خودکار و بدون عملیات منتقل می‌شوند.** هدف این است که کد، داده، فایل‌ها، تنظیمات و هویت‌ها با روش‌های استاندارد قابل استخراج، بازیابی و راه‌اندازی مجدد باشند.

## 2. مرزبندی وابستگی‌ها

معماری باید چهار لایه مستقل داشته باشد:

1. **منطق محصول:** کاربران، نقش‌ها، استاد، پوشه، کلاس، جلسه، انتشار، عضویت، بحث و جست‌وجو. این منطق نباید API اختصاصی یک میزبان را مستقیماً فراخوانی کند.
2. **قرارداد Backend API:** رابط نسخه‌دار و مستند که Android و Web از آن استفاده می‌کنند.
3. **آداپتورهای زیرساخت:** پیاده‌سازی قابل تعویض برای پایگاه داده، ذخیره فایل، ارسال پیام/ایمیل، احراز هویت و کش.
4. **محیط اجرا:** سرور، دامنه، TLS، شبکه، مانیتورینگ و پشتیبان‌گیری.

تعویض آداپتور یا میزبان نباید قرارداد API و منطق اصلی برنامه را تغییر دهد.

## 3. فناوری‌های قابل‌حمل و موارد ممنوع

- پایگاه داده مقصد: PostgreSQL استاندارد؛ از قابلیت‌های اختصاصی یک ارائه‌دهنده که جایگزین استاندارد ندارند استفاده نشود، مگر با ثبت دلیل و مسیر خروج.
- دسترسی به داده: لایه Repository/DAO و migrationهای نسخه‌دار؛ SQL و migrationها در مخزن Git نگهداری شوند.
- فایل‌ها: در صورت فعال‌شدن بارگذاری فایل، از رابط S3-compatible استفاده شود؛ نام bucket، endpoint و کلیدها تنظیمات محیط باشند، نه مقادیر ثابت در کد.
- Backend: به‌صورت container image قابل ساخت و اجرا در میزبان‌های سازگار بسته‌بندی شود. Dockerfile و فایل‌های اجرای محلی/staging/production نسخه‌بندی شوند.
- پیکربندی: آدرس دیتابیس، آدرس ذخیره‌سازی، دامنه، کلیدها و تنظیمات محیط فقط از environment/secrets خوانده شوند.
- زمان‌بندی و صف: در صورت نیاز از پروتکل/پیاده‌سازی استاندارد و قابل جایگزینی استفاده شود.
- از قفل‌شدن منطق برنامه در توابع serverless، triggerها، SDKهای دیتابیس یا سرویس‌های اختصاصی میزبان پرهیز شود. اگر استفاده ضروری شد، فقط پشت یک interface مستقل و با تست جایگزینی باشد.

## 4. قراردادهای فنی برای تعویض میزبان

- Backend باید stateless باشد؛ session یا فایل موقت مهم فقط روی دیسک محلی یک سرور نگهداری نشود.
- فایل‌های آپلودی (در صورت اضافه‌شدن) خارج از کانتینر و در storage مستقل قرار گیرند.
- کلیدها و اسرار در مخزن Git، APK، فایل عمومی سایت یا image کانتینر قرار نگیرند.
- health check، readiness check، log ساختاریافته و شناسه درخواست وجود داشته باشد.
- ساعت سرورها با UTC ذخیره شود و تبدیل منطقه زمانی فقط در لایه نمایش انجام شود.
- دامنه API از طریق تنظیمات محیط و DNS قابل تغییر باشد؛ برنامه Android نباید به IP ثابت یا دامنه میزبان خاص وابسته شود.
- نسخه API و نسخه schema پایگاه داده مستقل و قابل ردیابی باشند.
- عملیات حساس مهاجرت و import/export تکرارپذیر (idempotent) طراحی شوند.

## 5. استاندارد خروجی و بازیابی داده

برای جلوگیری از وابستگی به ابزار یک میزبان، خروجی قابل بازیابی باید برای هر بخش تعریف شود:

| بخش | قالب/روش خروجی الزامی |
|---|---|
| PostgreSQL | dump استاندارد قابل بازیابی با ابزارهای PostgreSQL، به‌علاوه export جدولی CSV/JSON برای داده‌های کلیدی |
| فایل‌ها | فایل‌های اصلی همراه manifest شامل کلید، اندازه، نوع محتوا، checksum و رابطه با رکورد |
| کاربران و نقش‌ها | خروجی شناسه داخلی، شناسه قدیمی، نقش‌ها، وضعیت و نگاشت هویت؛ بدون خروجی رمز عبور خام |
| محتوای آموزشی | JSON نسخه‌دار شامل استاد، پوشه، کلاس، دوره/درس، جلسه، متن اصلی، متن ویرایش‌شده، خلاصه، کلیدواژه، تاریخ و ترتیب |
| عضویت و انتشار | خروجی وضعیت انتشار، visibility، عضویت‌ها و مجوزهای کلاس خصوصی |
| تنظیمات | نمونه فایل تنظیمات بدون secret، همراه فهرست نام متغیرهای محیطی لازم |

شناسه‌های پایدار داخلی و شناسه‌های قدیمی Firebase باید در خروجی حفظ شوند. خروجی نباید صرفاً به نام نمایشی یا عنوان کلاس متکی باشد.

## 6. پشتیبان‌گیری و آزمون بازیابی

- backup دیتابیس و فایل‌ها باید مستقل از چرخه عمر سرور و حساب میزبانی اصلی نگهداری شود.
- دست‌کم یک نسخه پشتیبان رمزگذاری‌شده در مقصدی جدا از میزبان اصلی نگهداری شود.
- دوره نگهداری، تناوب backup و مسئولیت کنترل آن باید پیش از بهره‌برداری مشخص شود.
- backup موفق تلقی نمی‌شود مگر اینکه بازیابی آن در محیط جداگانه به‌صورت دوره‌ای آزمایش شده باشد.
- پس از هر تغییر مهم schema، یک backup پیش از migration و روش بازگشت مستند شود.
- معیارهای بازیابی شامل RPO (حداکثر داده قابل از دست‌رفتن) و RTO (حداکثر زمان قابل قبول برای بازگشت سرویس) پیش از انتشار عمومی تعیین شوند.
- پایان اعتبار یا حذف سرور نباید تنها نسخه داده را حذف کند؛ مالکیت حساب backup و دسترسی بازیابی باید مستقل از مالکیت سرور باشد.

## 7. چک‌لیست انتقال Backend به میزبان جدید

1. تهیه backup تازه و تأیید صحت آن.
2. ایجاد محیط مقصد و نصب نسخه سازگار پایگاه داده و runtime.
3. انتقال secrets از مسیر امن و تنظیم environment؛ نه از Git.
4. بازیابی dump دیتابیس و فایل‌ها و اجرای migrationهای لازم.
5. اجرای آزمون تطبیق تعداد رکوردها، شناسه‌ها، checksum فایل‌ها و رابطه‌های استاد/پوشه/کلاس/جلسه.
6. اجرای تست API، احراز هویت، نقش‌ها و مجوزهای مدیر/استاد/دانشجو.
7. اجرای آزمون staging با نسخه آزمایشی Android و Web.
8. کاهش TTL DNS در زمان مناسب، توقف نوشتن در مبدأ در بازه cutover، همگام‌سازی نهایی و تغییر DNS.
9. پایش خطاها و عملکرد؛ نگهداری مبدأ به‌صورت read-only تا پایان دوره اطمینان.
10. در صورت شکست معیارهای پذیرش، بازگشت DNS و سرویس به مبدأ و حفظ داده‌های ایجادشده در مقصد برای بررسی؛ از دوطرفه‌نویسی کنترل‌نشده پرهیز شود.

## 8. مهاجرت هویت و حساب کاربران

- شناسه داخلی کاربر مستقل از ارائه‌دهنده ورود باشد.
- اتصال حساب به Firebase UID یا هر شناسه ارائه‌دهنده دیگر در جدول نگاشت هویت ذخیره شود.
- نقش‌ها و مجوزهای محصول در دیتابیس خود درس‌یار نگهداری شوند، نه فقط در custom claims یا نقش‌های اختصاصی یک ارائه‌دهنده.
- رمز عبور کاربران از Firebase قابل استخراج فرض نشود. روش مهاجرت باید از قبل طراحی شود؛ مانند ورود مجدد امن، بازیابی رمز یا اتصال تدریجی حساب پس از اثبات مالکیت.
- تا زمانی که مهاجرت هویت آزموده نشده، ورود فعلی کاربران مختل نشود.

## 9. آزمون‌های پذیرش قابلیت انتقال

این موارد باید در CI یا محیط staging آزموده شوند:

- اجرای Backend با متغیرهای محیطی متفاوت، بدون تغییر کد.
- ساخت و اجرای container image روی محیط سازگار مستقل از میزبان اولیه.
- ساخت دیتابیس خالی با اجرای تمام migrationها از ابتدا.
- export و import داده آزمایشی و تطبیق شناسه‌ها و تعداد رکوردها.
- بازیابی backup در یک محیط جداگانه.
- اجرای API و تست مجوزها پس از restore.
- اجرای Android و Web با تغییر آدرس API از تنظیمات انتشار، بدون تغییر منطق برنامه.
- اثبات اینکه قطع دسترسی به میزبان قبلی مانع بازیابی backup مستقل نمی‌شود.

## 10. مراحل اجرایی و محدودیت فعلی

1. ابتدا قرارداد داده، API و مرز آداپتورها تثبیت شود.
2. سپس Backend مستقل و قابل اجرا در staging ساخته شود؛ هنوز هیچ داده واقعی منتقل نشود.
3. export/import و restore با داده آزمایشی و نسخه پشتیبان آزمایش شود.
4. سایت و اپلیکیشن به API مشترک متصل شوند.
5. فقط پس از موفقیت آزمون‌ها و تأیید صریح، درباره انتخاب میزبان و مهاجرت داده واقعی تصمیم‌گیری شود.

در این مرحله:
- Firebase فعلی منبع عملیاتی باقی می‌ماند.
- سرور ایران خریداری یا راه‌اندازی نمی‌شود.
- هیچ DNS، حساب، قانون Firebase یا داده تولیدی تغییر نمی‌کند.
- این سند الزام معماری است و به‌تنهایی مجوز انتقال یا حذف هیچ سرویس فعلی نیست.
