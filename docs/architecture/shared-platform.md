# درس‌یار: معماری سکوی مشترک اندروید و وب

وضعیت: طرح اجرایی مرحله‌ای؛ هنوز هیچ تغییری در داده‌های تولیدی یا تنظیمات Firebase اعمال نشده است.

## 1. هدف

اپلیکیشن اندروید و سایت درس‌یار باید دو رابط برای یک سکوی آموزشی واحد باشند؛ نه دو سامانه با کاربران و داده‌های جداگانه. اطلاعات استاد، کلاس، جلسه، انتشار، عضویت و محتوای آموزشی باید از یک API و یک منبع داده مشترک خوانده و مدیریت شوند.

## 2. اصول غیرقابل‌تغییر

- ساختار آموزشی فعلی حفظ می‌شود: **استاد ← کلاس ← جلسه**. در صورت وجود پوشه‌های استاد در مدل فعلی، آن‌ها نیز حفظ می‌شوند و پوشه جایگزین کلاس یا استاد نیست.
- شناسه‌های فعلی کلاس‌ها و جلسات تا حد امکان در مهاجرت حفظ می‌شوند؛ هیچ مهاجرتی نباید بدون نسخه پشتیبان و تطبیق تعداد/شناسه‌ها انجام شود.
- Room در اندروید برای تجربه محلی و آفلاین باقی می‌ماند.
- Firebase در دوره توسعه موازی دست‌نخورده می‌ماند و تا تأیید مهاجرت، منبع عملیاتی فعلی است.
- مجوزها فقط در رابط کاربری کنترل نمی‌شوند؛ API باید در سمت سرور آن‌ها را اعمال کند.
- کلیدهای سرویس و اسرار سرور هرگز داخل APK یا کد عمومی سایت قرار نمی‌گیرند.
- سرویس‌های هوش مصنوعی و تبدیل گفتار مستقل از مهاجرت پایگاه داده باقی می‌مانند، مگر اینکه جداگانه تصمیم‌گیری شود.

## 3. معماری مقصد

```
Android app (Room / offline cache)       Responsive web site
                 \                         /
                  \                       /
                     HTTPS Backend API
                             |
                 Authentication + RBAC
                             |
                       PostgreSQL
                             |
               Optional S3-compatible storage
```

- **Backend API:** مرجع واحد احراز هویت، مجوزها، انتشار و عملیات داده.
- **PostgreSQL:** داده‌های ساختاریافته و رابطه‌های آموزشی.
- **Object storage:** در فاز نخست برای صوت استفاده نمی‌شود؛ در صورت نیاز آینده برای فایل‌های بارگذاری‌شده قابل افزودن است.
- **Web site:** صفحات عمومی استاد/کلاس و محیط خصوصی دانشجو و استاد را از همان API دریافت می‌کند.
- **Android:** به‌تدریج از طریق لایه Repository به API متصل می‌شود و Room را برای cache و کار آفلاین نگه می‌دارد.

## 4. مدل مفهومی داده

مدل مقصد باید حداقل این مفاهیم را پوشش دهد:

- User: شناسه داخلی، شناسه هویت قدیمی (در صورت وجود)، وضعیت و اطلاعات نمایشی.
- Role / approval: نقش کاربر (مدیر اصلی، استاد، دانشجو) و وضعیت تأیید استاد.
- TeacherFolder: پوشه‌های متعلق به استاد و ترتیب/وضعیت نمایش آن‌ها.
- Class: مالک استاد، پوشه اختیاری، عنوان، توضیحات، وضعیت انتشار و visibility.
- Lecture/Session: کلاس والد، عنوان، تاریخ، متن اصلی و ویرایش‌شده، خلاصه، کلیدواژه‌ها و ترتیب.
- Enrollment / access code: عضویت دانشجو و دسترسی به کلاس خصوصی.
- AudioSource: یک یا چند مرجع صوتی برای جلسه، نوع منبع، URL، عنوان اختیاری، وضعیت بررسی و زمان آخرین اعتبارسنجی.
- Publication: وضعیت و دامنه انتشار؛ نباید با مالکیت محتوا یکی فرض شود.
- Sync metadata: نسخه، زمان به‌روزرسانی و شناسه‌های سازگار برای همگام‌سازی.

مالکیت جلسه باید از رابطه والد معتبر (کلاس/درس) به‌طور قطعی قابل تعیین باشد؛ در صورت نیاز مالکیت صریح نیز ذخیره شود تا مجوزها مبهم نباشند.

## 5. مجوزها (الزام سمت سرور)

| نقش | مجوز |
|---|---|
| مدیر اصلی | مشاهده، ایجاد، ویرایش، انتشار، پنهان‌سازی و حذف محتوای همه استادان |
| استاد | مدیریت پوشه‌ها، کلاس‌ها و جلسات متعلق به خود |
| استاد | مشاهده محتوای منتشرشده دیگران فقط به‌صورت خواندنی |
| دانشجو | مشاهده کلاس‌های عمومی و کلاس‌های خصوصی‌ای که مجاز به آن‌ها شده است |
| بازدیدکننده | مشاهده فقط صفحات و کلاس‌های عمومی منتشرشده |

قواعد تکمیلی:
- نقش مدیر از داده معتبر سمت سرور خوانده شود؛ هرگز به پارامتر ارسالی از کلاینت اعتماد نشود.
- کد ورود کلاس خصوصی به‌صورت امن نگهداری شود (ترجیحاً hash) و محدودیت تلاش/انقضا داشته باشد.
- عمومی‌بودن صفحه به معنی اجازه ویرایش نیست.
- حذف و تغییر مالکیت باید audit log داشته باشد.
- خطای عدم مجوز باید بدون افشای داده خصوصی بازگردانده شود.

## 6. انتشار عمومی و خصوصی

هر کلاس باید visibility صریح داشته باشد:
- `public`: صفحه عمومی قابل مشاهده در سایت و در صورت نیاز قابل نمایه‌سازی.
- `private`: فقط اعضای مجاز و مدیر اصلی.
- `unlisted` (اختیاری): با لینک قابل دسترسی، بدون نمایش در فهرست عمومی؛ فقط اگر سیاست محصول آن را تأیید کند.

کلاس خصوصی می‌تواند با کد ورود، دعوت یا تأیید استاد قابل دسترسی شود. کد ورود باید به کلاس مشخص متصل باشد و پس از پذیرش، عضویت ثبت شود؛ کد نباید در URL یا محتوای عمومی افشا شود.

## 7. پشتیبانی صوت با لینک خارجی

فاز نخست فایل صوتی را روی سرور درس‌یار بارگذاری نمی‌کند.

- برای هر جلسه یک یا چند AudioSource ذخیره می‌شود.
- انواع اولیه: لینک مستقیم فایل صوتی، لینک صفحه پخش/میزبان، و لینک خارجی عمومی.
- پخش داخل برنامه/سایت فقط وقتی تضمین می‌شود که منبع با روش استاندارد مرورگر/اندروید سازگار باشد؛ لینک صفحه یا سرویس محدودشده ممکن است فقط در مرورگر باز شود.
- پیش از ذخیره، URL از نظر قالب و پروتکل اعتبارسنجی شود. بررسی دسترسی باید در سمت سرور با محافظت SSRF انجام شود؛ سرور نباید URL دلخواه داخلی یا خصوصی را واکشی کند.
- برای جلوگیری از SSRF، آدرس‌های localhost، شبکه‌های خصوصی، link-local، پورت‌ها و schemeهای غیرمجاز مسدود شوند؛ redirectها نیز دوباره اعتبارسنجی شوند.
- پخش‌کننده باید حالت‌های «پخش داخلی ممکن نیست» و «بازکردن منبع اصلی» داشته باشد.
- ذخیره موقعیت پخش در سطح کاربر و جلسه اختیاری است.
- معماری AudioSource مستقل از فایل باشد تا در آینده نوع `uploaded_asset` بدون تغییر مدل جلسه اضافه شود.
- هیچ پراکسی صوتی یا دانلود خودکار فایل در فاز نخست پیاده‌سازی نشود.

## 8. API سطح بالا

نام‌ها نمونه‌اند و پیش از پیاده‌سازی با قرارداد نهایی API تثبیت می‌شوند:

- `POST /api/v1/auth/login`, `POST /api/v1/auth/refresh`, `POST /api/v1/auth/logout`
- `GET /api/v1/me`
- `GET /api/v1/teachers/{teacherId}`
- `GET /api/v1/classes`, `GET /api/v1/classes/{classId}`
- `POST/PATCH/DELETE /api/v1/classes/{classId}`
- `GET/POST/PATCH/DELETE /api/v1/classes/{classId}/sessions`
- `GET/POST/PATCH/DELETE /api/v1/sessions/{sessionId}/audio-sources`
- `POST /api/v1/classes/{classId}/join`
- `GET /api/v1/me/enrollments`
- `/api/v1/admin/**` برای عملیات مدیر اصلی
- مسیرهای sync نسخه‌دار برای اندروید، پس از تعریف سیاست تعارض و idempotency.

تمام مسیرهای نوشتن باید احراز هویت، مجوز مالکیت/نقش، اعتبارسنجی ورودی و ثبت audit مناسب داشته باشند.

## 9. هویت و مهاجرت Firebase

- UIDهای Firebase به‌عنوان شناسه قدیمی پایدار نگهداری یا به شناسه داخلی نگاشت شوند؛ نگاشت باید یکتا و قابل بازبینی باشد.
- رمزهای عبور Firebase قابل انتقال مستقیم فرض نمی‌شوند. طرح ورود مجدد/بازیابی رمز باید پیش از cutover تعیین شود.
- ابتدا export و backup کامل Firestore و snapshot داده‌های Room تهیه شود.
- مهاجرت آزمایشی روی staging اجرا شود و شمارش رکوردها، شناسه‌ها، رابطه استاد-کلاس-جلسه، مالکیت، انتشار و دسترسی‌ها تطبیق داده شود.
- تا پایان آزمون پذیرش، Firebase منبع اصلی باقی می‌ماند. dual-write بدون طراحی idempotency و حل تعارض ممنوع است.
- cutover فقط با برنامه rollback و تأیید صریح انجام شود.

## 10. فازهای اجرا

1. **ممیزی و قرارداد داده:** تطبیق Entityهای Room، مدل Firestore، نقش‌ها، قواعد فعلی و شناسه‌ها.
2. **Backend مستقل در staging:** schema، migrationها، auth، RBAC، API و تست‌های مجوز.
3. **نمونه سایت متصل به API:** صفحه استاد، فهرست کلاس‌های عمومی، صفحه کلاس/جلسه و ورود به کلاس خصوصی.
4. **اتصال اندروید:** افزودن remote data source و حفظ Room؛ انتقال تدریجی، نه بازنویسی یک‌باره.
5. **مهاجرت آزمایشی:** import، تطبیق داده و آزمون نقش‌ها و ساختار پوشه/کلاس/جلسه.
6. **انتقال کنترل‌شده:** فقط پس از آزمون و تأیید؛ با امکان بازگشت.
7. **افزودن قابلیت‌های بعدی:** بارگذاری فایل صوتی، فضای ابری، پرداخت یا امکانات دیگر فقط در صورت نیاز.

## 11. معیارهای پذیرش

- تغییر مجاز در اپلیکیشن در سایت با همان حساب و داده دیده شود و برعکس.
- مدیر اصلی بتواند محتوای تمام استادان را مدیریت کند.
- استاد عادی نتواند محتوای استاد دیگر را تغییر یا حذف کند.
- دانشجو نتواند کلاس خصوصی بدون مجوز را مشاهده کند.
- ساختار استاد ← پوشه ← کلاس ← جلسه و شناسه‌های قبلی حفظ شوند.
- لینک صوت معتبر در هر دو کلاینت قابل پخش یا بازکردن باشد و لینک نامعتبر پیام روشن بدهد.
- داده‌های قدیمی، متن اصلی، متن ویرایش‌شده و اطلاعات جلسات در مهاجرت حذف یا بازنویسی ناخواسته نشوند.
- تست‌های API برای مجوزهای مثبت و منفی و تست مهاجرت موفق باشند.

## 12. مواردی که هنوز نیازمند انتخاب/تأیید هستند

- ارائه‌دهنده میزبانی و دیتابیس نهایی و محل استقرار.
- دامنه سایت و زیردامنه API.
- روش ورود نهایی (ایمیل/رمز، تلفن/OTP یا ترکیبی).
- فناوری و محل میزبانی فرانت‌اند سایت.
- سیاست دقیق کلاس خصوصی و انقضای کد ورود.
- سیاست بازیابی/تغییر رمز برای حساب‌های فعلی Firebase.

تا تعیین این موارد و فراهم‌شدن دسترسی‌های محیط staging، هیچ سرویس ابری خریداری یا مستقر نمی‌شود و هیچ داده تولیدی جابه‌جا نمی‌شود.
