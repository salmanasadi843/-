# گزارش ممیزی فنی درس‌یار برای Backend مشترک و قابل‌انتقال

تاریخ ممیزی: 2026-10-31
مبنای بررسی: شاخه `main` مخزن Android و فایل‌های فعلی Room، همگام‌سازی Firestore، ورود و قواعد Firestore.
دامنه: ممیزی ایستا؛ هنوز به Firebase عملیاتی یا دستگاه کاربر متصل نشده‌ایم و هیچ داده‌ای export/import یا تغییر داده نشده است.

## 1. جمع‌بندی اجرایی

- اپلیکیشن فعلی Android + Room + Firebase Auth/Firestore است؛ در مخزن فعلی Backend مستقل یا قرارداد API عملیاتی برای محتوای آموزشی مشاهده نشد.
- مدل محلی واقعی شامل `TeacherFolderEntity`، `ClassEntity`، `CourseEntity` و `LectureEntity` است. بنابراین مدل مقصد باید ساختار **استاد ← پوشه ← کلاس ← درس/دوره ← جلسه** را پوشش دهد؛ پوشه اختیاری است و نباید کلاس یا استاد را جایگزین کند.
- Firebase تا زمان پذیرش کامل Backend جدید باید منبع عملیاتی باقی بماند.
- پیش از هر انتقال واقعی، باید ممیزی داده‌های بدون مالک، شناسه‌های محلی، پشتیبان‌ها و انتشارها کامل شود.
- هیچ تغییر Room یا Firebase در این مرحله مجاز نیست.

## 2. یافته‌ها و ریسک‌ها

### بحرانی — پشتیبان‌گیری خصوصی، دو جلسه را بر اساس عنوان حذف می‌کند

در `FirestoreSyncRepository.uploadSnapshot` دو عنوان جلسه با `filterNot` از backup خصوصی حذف می‌شوند. این منطق برای مهاجرت عمومی و کامل قابل قبول نیست؛ عنوان، معیار هویت یا مجوز حذف نیست. در مسیر انتقال، تمام رکوردها باید منتقل شوند و هر استثنا باید با شناسه، دلیل، تأیید صاحب داده و گزارش تطبیق ثبت شود.

### بحرانی — بازیابی Firestore به‌صورت تراکنشی کامل انجام نمی‌شود

در `validateAndReplaceLocalData` ابتدا جدول‌های محلی پاک و سپس رکوردها درج می‌شوند؛ این عملیات در کد ممیزی‌شده داخل `RoomDatabase.withTransaction` نیست. توقف برنامه یا خطا در میانه می‌تواند مجموعه محلی ناقص ایجاد کند. هر بازیابی آینده باید در یک تراکنش Room انجام شود و قبل از commit، تعداد رکوردها، شناسه‌ها و روابط والد/فرزند اعتبارسنجی شوند.

### بالا — fallback مخرب Room فعال است

`AppDatabase` نسخه 8 است، `exportSchema = false` دارد و `fallbackToDestructiveMigration(true)` فعال است. تغییر schema بدون مسیر migration معتبر می‌تواند داده محلی را حذف کند. در فاز معماری، Entityهای فعلی را تغییر نمی‌دهیم. پیش از هر تغییر آینده باید schema export، تست migration از نسخه‌های پشتیبانی‌شده و backup/restore آزمایش شود. حذف fallback نیز باید در PR مستقل و پس از بررسی مسیرهای migration انجام شود، نه هم‌زمان با مهاجرت Backend.

### بالا — شناسه‌های Room برای هویت جهانی کافی نیستند

شناسه‌های Room عددی و auto-generated هستند و در دستگاه‌ها/نصب‌های مختلف می‌توانند تکرار شوند. کلاس مالک `ownerUid` دارد؛ اما Course و Lecture مالکیت صریح ندارند و از رابطه والد استنتاج می‌شود. پوشه نیز `ownerUid` دارد. شناسه محلی باید به‌عنوان legacy key نگهداری شود، نه شناسه جهانی مقصد. نگاشت باید حداقل با ترکیب منبع، مالک قدیمی، نوع رکورد و شناسه محلی یکتا باشد.

### بالا — رکوردهای کلاس با مالک خالی وجود دارند

در backup خصوصی، کلاس‌هایی با `ownerUid == uid` یا `ownerUid.isBlank()` پذیرفته می‌شوند. این یعنی بخشی از داده‌های قدیمی ممکن است مالکیت قطعی نداشته باشند. این رکوردها نباید خودکار به حسابی نسبت داده شوند. باید در گزارش staging به‌عنوان `ownership_unresolved` جدا شوند و پیش از انتشار یا انتقال نهایی تعیین تکلیف شوند.

### بالا — همگام‌سازی مطالب منتشرشده، داده‌ها را ادغام و حذف تکراری می‌کند

در `CloudMaterialsSync` شناسه منفی پایدار برای داده‌های اشتراکی ساخته می‌شود و کلاس‌ها/جلسات با ترکیب نام استاد، عنوان، درس و تاریخ fingerprint یا deduplicate می‌شوند. این رفتار برای نمایش اشتراکی فعلی مفید است، اما نباید به مهاجرت مالکانه تبدیل شود؛ دو کلاس هم‌نام ممکن است دو موجودیت مستقل باشند. در مقصد، رکورد اصلی هر استاد باید جدا بماند و فقط نمای اشتراکی/جست‌وجو می‌تواند تجمیع نمایشی انجام دهد.

### بالا — backup JSON محلی همه فیلدهای Entity را حفظ نمی‌کند

در `DatabaseBackup` خروجی فعلی برخی فیلدها را ندارد؛ از جمله `originalTranscript`، `isPublished` جلسه و `aiQuizJson` در export محلی. مسیر import نیز کل جدول‌ها را جایگزین می‌کند. این فایل نسخه 1 را نباید تنها منبع مهاجرت کامل تلقی کرد. قبل از استفاده باید نسخه جدید export با پوشش تمام فیلدها، manifest، checksum، preview و restore آزمایشی طراحی شود. فایل صوتی محلی `audioFilePath` عمداً قابل انتقال مستقیم فرض نمی‌شود؛ فقط وجود/عدم وجود و مسیر تصمیم‌گیری آن باید گزارش شود.

### بالا — تشخیص مدیر اصلی در کلاینت و قواعد Firebase وابسته به شناسه ثابت است

`AuthPreferences` نقش اصلی را با ایمیل تشخیص می‌دهد و `firestore.rules` نیز تابع مدیر اصلی و یک UID ثابت برای استاد فعال دارد. در Backend، مجوز مدیر باید از نقش معتبر سمت سرور خوانده شود؛ هیچ ایمیل، نقش ارسالی کلاینت یا مقدار SharedPreferences مجوز قطعی ایجاد نمی‌کند. مدیر اصلی باید در فرایند bootstrap امن و خارج از کد منبع provision شود و تمام تغییرات مدیریتی audit شوند.

### متوسط — قواعد و مسیرهای Firebase بیش از مدل چهار جدول Room هستند

قواعد فعلی شامل `users`، زیرمجموعه‌های خصوصی کاربران، `teacher_requests`، `approved_teachers`، `shared`، `shared_materials`، `published_classes`، `published_lessons`، `publication_index` و `teacher_data/{uid}/records` است. این مسیرها معادل مستقیم Entityهای Room نیستند. ممیزی مهاجرت باید export مستقل هر مجموعه و subcollection، شمارش اسناد، مالک، سطح دسترسی، ارجاع‌ها و نسخه schema را پوشش دهد.

### متوسط — علاقه‌مندی، داده شخصی کاربر است

`LectureEntity.isFavorite` در مدل محلی است، اما نباید به‌عنوان ویژگی عمومی جلسه در دیتابیس مشترک ذخیره شود؛ در مدل مقصد باید به جدول وضعیت شخصی هر کاربر/جلسه منتقل شود. همین قاعده برای موقعیت پخش و تنظیمات شخصی برقرار است.

### متوسط — فایل صوتی و لینک صوتی دو مفهوم متفاوت‌اند

`audioFilePath` مسیر محلی دستگاه است و قابل انتقال به سرور نیست. `audioUrl` مرجع بیرونی است و در فاز اول باید حفظ شود. هیچ فایل صوتی بدون تصمیم جداگانه و manifest فایل‌ها بارگذاری یا حذف نشود.

## 3. نقشه داده واقعی و مقصد

| مدل Room فعلی | مالکیت فعلی | مقصد |
|---|---|---|
| TeacherFolderEntity | ownerUid | teacher_folders |
| ClassEntity | ownerUid؛ ممکن است خالی باشد | teaching_classes |
| CourseEntity | از classId | teaching_courses |
| LectureEntity | از classId/courseId؛ هر دو nullable | teaching_sessions |
| isFavorite | محلی/شخصی | user_session_state |
| audioFilePath | مسیر محلی دستگاه | گزارش جداگانه؛ انتقال خودکار ممنوع |
| audioUrl | URL بیرونی | session_audio_sources / legacy_audio_url |

مدل مقصد باید متن خام و ویرایش‌شده را مستقل نگه دارد، همچنین خلاصه، نکات کلیدی، آزمون JSON، برچسب‌ها، ترتیب دستی، تاریخ جلسه، وضعیت انتشار و لینک صوت را پوشش دهد.

## 4. هویت و مجوزها

- `app_users` شناسه داخلی UUID دارد.
- `auth_identities` اتصال قابل تعویض به Firebase UID یا ارائه‌دهنده بعدی را نگه می‌دارد.
- نقش‌های محصول در `app_roles` نگهداری می‌شوند؛ نقش Firebase به‌تنهایی مرجع مجوز مقصد نیست.
- تأیید استاد و تعلیق حساب در پروفایل سمت سرور ثبت می‌شود.
- مدیر اصلی از bootstrap امن سمت سرور تعیین می‌شود؛ هیچ UID یا ایمیل مدیر در APK یا کد عمومی قرار نمی‌گیرد.
- استاد فقط مالکیت خود را تغییر می‌دهد؛ مشاهده محتوای منتشرشده دیگران خواندنی است.
- مدیر اصلی مجاز به مدیریت همه محتواست.
- دانشجو فقط محتوای عمومی یا کلاس خصوصی دارای عضویت فعال را می‌بیند.
- هر عملیات نوشتن API باید مالکیت، نقش، اعتبارسنجی و audit log داشته باشد.

## 5. معماری اجرایی پیشنهادی

### Backend

پیشنهاد اولیه: **Kotlin + Ktor** به‌صورت سرویس مستقل و stateless، با REST API نسخه‌دار. این انتخاب زبان را با Android فعلی همسو می‌کند و Backend را از Android SDK و Firebase Firestore جدا نگه می‌دارد.

- PostgreSQL برای داده‌های رابطه‌ای
- Flyway برای migrationهای نسخه‌دار
- JDBC/HikariCP یا لایه repository ساده و قابل تست
- Firebase Admin SDK فقط در آداپتور احراز هویت مرحله گذار برای اعتبارسنجی Firebase ID Token؛ نه برای دسترسی مستقیم کلاینت به Firestore در منطق کسب‌وکار
- Docker image برای اجرای قابل‌انتقال
- OpenAPI برای قرارداد API
- تست‌های integration با PostgreSQL واقعی/کانتینری و تست‌های مجوز

این انتخاب هنوز به معنی نصب سرور یا افزودن وابستگی به اپلیکیشن نیست؛ ابتدا یک نمونه staging مستقل ساخته و ارزیابی می‌شود.

### کلاینت‌ها

- Android: Room حفظ می‌شود؛ Repository به دو پیاده‌سازی Local و Remote تفکیک می‌شود. تغییر منبع داده از تنظیمات build/runtime کنترل می‌شود.
- Web: مستقیماً از همان Backend API استفاده می‌کند.
- هیچ کلاینتی به PostgreSQL یا کلیدهای سرویس دسترسی مستقیم ندارد.
- تا پایان cutover، Firebase مسیر عملیاتی فعلی باقی می‌ماند؛ dual-write بدون طراحی نسخه و حل تعارض ممنوع است.

## 6. داده‌های نیازمند بررسی تکمیلی قبل از import

1. تمام اسناد Firestore در مجموعه‌ها و subcollectionهای ذکرشده، همراه با شمارش و مالکیت.
2. کلاس‌های دارای ownerUid خالی و جلسات فاقد classId یا courseId.
3. تطبیق backup خصوصی هر استاد با داده‌های Room و نسخه‌های منتشرشده.
4. اسناد قدیمی shared_materials که payload یا schemaVersion متفاوت دارند.
5. شناسه‌های منفی تولیدشده برای داده‌های اشتراکی؛ این شناسه‌ها هرگز شناسه اصلی مقصد نیستند.
6. فایل‌های صوتی محلی و URLهای بیرونی؛ فقط inventory، بدون انتقال خودکار.
7. هر نوع بحث/نظر، یادداشت یا تعامل دانشجو که در Firestore یا نسخه‌های قبلی ذخیره شده و هنوز در schema مقصد فهرست نشده است.
8. حساب مدیر اصلی و استادان تأییدشده؛ نگاشت با تأیید مالک داده و بدون اعتماد به مقدار نقش کلاینت.

## 7. معیار پذیرش ممیزی و مهاجرت آزمایشی

- برای هر نوع رکورد، تعداد منبع و مقصد، تعداد ردشده‌ها و علت رد گزارش شود.
- هیچ رکوردی به علت عنوان، شباهت محتوا یا ID منفی حذف/ادغام نشود.
- هر رکورد کلاس/درس/جلسه مالک یا وضعیت unresolved صریح داشته باشد.
- همه شناسه‌های قدیمی در جدول نگاشت قابل بازیابی باشند.
- متن اصلی و ویرایش‌شده، خلاصه، کلیدواژه، آزمون، ترتیب، تاریخ و لینک صوت با checksum/مقایسه فیلدها تطبیق داده شوند.
- مجوز مدیر/استاد/دانشجو با تست مثبت و منفی اثبات شود.
- backup در مقصدی جدا بازیابی شود و سرویس بدون میزبان مبدأ بالا بیاید.
- هیچ cutover یا تغییر Firebase بدون تأیید صریح انجام نشود.

## 8. محدوده این مرحله

این سند فقط نتیجه ممیزی ایستا و تصمیم‌های طراحی است. داده تولیدی، Firestore rules، Firebase Auth، Room schema، APK، DNS و سرویس میزبانی تغییر نکرده‌اند. هیچ داده‌ای جابه‌جا یا حذف نشده است.
